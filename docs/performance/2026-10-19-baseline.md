# Baseline Load Test — 2026-10-19 (current implementation)

Re-measured with `npm run loadtest` (autocannon) against the Docker Compose stack
**after** the Redis removal, so the rate-limiter path in these numbers is the
current bounded in-process store. A single development machine — numbers
characterize that environment only; they are not a production capacity claim.

## Environment

| Item | Value |
|------|-------|
| Date | 2026-10-19, 22:53 UTC |
| Host | Linux x86_64 (WSL2), 12 CPU cores, 7.9 GB RAM |
| App runtime | `node:22-alpine` (Node.js 22) in Docker Compose, single container |
| Database | PostgreSQL 16.15 (`postgres:16-alpine`) in Docker Compose |
| Rate limiter | Bounded in-process store; `RATE_LIMIT_MAX=10000000` for the measurement window only (production default is 100 req/60 s per layer) |
| Code state | `main` @ `b098f05` |
| Load generator | autocannon 7.15.0 via `npm run loadtest` on the host (target `http://localhost:3000`) |

## Method

- Account-scoped `POST /usage`, `units=1`, unique idempotency key per
  request, pipelining 1 (no request pipelining; each response awaited).
- Load-test account bootstrapped with `bootstrap-loadtest.ts`
  (account plan: 1,000,000 units/month, 10,000 max/request).
- Every sent request is an authenticated write: counter row lock +
  `usage_requests` insert in one transaction.

### About p95

This report intentionally omits p95. `autocannon` computes a fixed histogram and
emits `p50`, `p75`, `p90`, `p97_5`, and `p99` — it does **not** emit `p95`.
Rather than interpolate a number autocannon never measured, this report uses the
nearest real percentiles (`p90` and `p97_5`).

Throughput is connection-latency-bound: 10 connections at ~82 ms mean latency
implies ≈121 req/s, which matches the measured 120.44 req/s. The dominant cost
is the per-request database transaction (counter row-lock upsert +
decision-log insert + commit).

For context only: the removed 2026-10-18 baseline (Redis-era stack) measured
the same plateau, 120.40 req/s at 82.23 ms mean latency, with a heavier tail
(p99 546 ms vs 146 ms here). Two single runs on one machine — no significance
is claimed beyond "same bottleneck, same ceiling".

## Reproduction

```bash
# 1. Raise the rate limit for the measurement window
#    (the .env default of 100 is restored in step 5)
RATE_LIMIT_MAX=10000000 docker compose up -d app

# 2. Bootstrap the load-test account and capture the printed key
docker compose run --rm \
  -e BOOTSTRAP_ACCOUNT_NAME=loadtest-account \
  -e BOOTSTRAP_API_KEY_NAME=loadtest-key \
  app node dist/scripts/bootstrap-loadtest.js

# 3. Run the baseline (key from the previous step)
export LOADTEST_API_KEY=<key-from-step-2>
npm run loadtest -- --duration 30 --connections 10

# 4. Verify accounting invariants
docker compose run --rm app node dist/scripts/verify-invariants.js

# 5. Restore the production-representative rate limit
docker compose up -d app
# confirm: docker exec usage-metering-app printenv RATE_LIMIT_MAX  ->  100
```

The load test refuses non-localhost targets (`validateLocalUrl`).

## Limitations

- Single WSL2 machine: load generator, application, and PostgreSQL share 12
  vCPUs. No TLS, reverse proxy, or multiple app replicas.
- The rate limit was raised for the window; the default 100 req/60 s produces
  429s by design and was not part of this measurement.
- One 30 s run — no repeated trials or confidence intervals.
- `synchronous_commit=on`; throughput is bound by the serialized per-account
  counter commit path — the intended no-overspend design, not an HTTP or CPU
  ceiling.
- Not re-run for every change.
