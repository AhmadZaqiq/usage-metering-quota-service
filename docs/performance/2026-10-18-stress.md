High-intensity progressive stress test of the Usage Metering & Quota Service on the local Docker Compose stack, with accounting-invariant verification before, during, and after load.

Raw artifacts: [`2026-10-18-stress-raw/`](2026-10-18-stress-raw/) (stage logs, resource samples, invariant outputs, demo log, test-suite log, storm results).

> These are **local single-container benchmark results on a WSL2 development host — not production capacity**. No TLS, no reverse proxy, single app instance.

## 6. Resource Monitoring

Sampled every 2s across all stages (`2026-10-18-stress-raw/resources.log`):

| Metric | Peak | Interpretation |
|---|---|---|
| App container CPU | 123.5% (≈1.2 of 12 cores) | Not host-CPU-bound |
| PostgreSQL container CPU | 84.6% | Not CPU-bound; dominated by lock waits |
| Redis CPU | 8.0% | Idle-ish; 429 path is cheap |
| Host load1 | 3.08 / 12 | **Load generator was NOT CPU-bound** — the ~110 rps ceiling is server-side |
| PG connections | 21 (pool 20 + 1 admin) | Pool cap hit at every stage ≥25 |
| PG connections waiting | **20** | Entire pool blocked on locks during load |
| App memory | 192 MiB peak | Stable, no leak signal over the campaign |
| PG memory | 81 MiB peak | Stable |

**Direct bottleneck evidence** (live sample during stage D, 100 connections):

```
wait_event_type | wait_event     | state  | count
Lock            | transactionid  | active |   19
pg_locks WHERE NOT granted        |        |   18
```

19 of 20 pooled connections were waiting on **`Lock:transactionid`** — the row lock on the single shared **account-level `usage_counters` row**, acquired by `upsertAndLockCounter` and held to commit. This is the **designed per-account serialization that prevents overspend**: all requests against one account's monthly counter form a strict queue. At ~9 ms critical-section time, the ceiling is ≈1/0.009 ≈ 110 rps — exactly the measured plateau.

| Class | Count | Detail |
|---|---|---|
| Expected business rejections (quota) | 0 | Allowance raised; every completed 2xx carried `decision: accepted` |

| Infrastructure saturation | **700 non-2xx + 1 timeout** | HTTP **500 `INTERNAL_ERROR`**: pg pool `connectionTimeoutMillis` (5s) expired while waiting for one of 20 pool slots — queue depth at 1,000 conns (≈9s mean wait) exceeds 5s. | Application defects | **0** | No invariant violation, no accounting drift, no 4xx misclassification, no crash (app stayed healthy throughout) |

Post-stage probes confirmed correctness during overload: sequential curl probes interleaved with an 800-connection hammer all returned 200 with monotonically decreasing `accountRemaining`.

## 8. Bottleneck Analysis

1. **Primary (by design): per-account counter row lock.** One `usage_counters` row per (account, period, user-null) serializes the entire commit path for that account. Evidence: 19× `Lock:transactionid` waits; flat ~110 rps across 50× concurrency range; app/db CPU modest. This is the price of the "no overspend under concurrency" invariant — correctness over throughput, per the project's stated goals.
2. **Secondary: pg pool max = 20.** Caps concurrent DB work; contributes queueing but is not the serialization point (a bigger pool would still serialize on the row lock).
3. **Tertiary (failure mode at 1,000 conns): pool acquire timeout 5s.** Converts extreme queue depth into 500s rather than unbounded memory growth — a deliberate fail-fast behavior.
4. **Not bottlenecks:** host CPU (load1 ≤ 3.08/12), app CPU (≤1.2 cores), PG CPU (≤85%), Redis (≤8%), memory (stable), load generator (not CPU-bound).

**Scaling implication (untested here):** throughput scales with the number of *independent hot accounts* (each has its own counter row), not with concurrency against one account. Horizontal app scaling would likewise multiply per-account throughput only if paired with counter sharding or lock-free designs — out of scope of this run.

## 9. Executive Summary

- **Sustained rate:** ~**110–114 req/s** against a single hot account (flat from 10 to 500 connections; 6,813 requests over 60s at 500 conns with zero failures).
- **Latency at that load:** p50 **21 ms** at 10 conns (uncontended), **293 ms** at 50, **4.27 s** at 500 (queueing, not processing). At saturation, latency is almost entirely lock-queue wait.
- **Unexpected failures:** **zero** up to and including 500 connections sustained. At 1,000 connections: 700 × HTTP 500 (pool acquire timeout) + 1 client timeout — saturation behavior, not corruption.
- **Accounting under concurrency:** **correct throughout** — all 8 invariants hold before and after; rejected requests consumed nothing (+0 rejected rows); the 200-way idempotency storm consumed exactly 1 unit and persisted exactly 1 row; `Acme Corp` untouched (isolation exact); counter delta equals accepted sum to the unit.
- **First demonstrated bottleneck:** the **account-counter row lock** (`Lock:transactionid`), an intentional correctness mechanism capping one account at ≈110 rps on this hardware; the first *failure mode* appears at 1,000 connections when the 5 s pool-acquire timeout converts queue depth into 500s.

## 10. Reproduction

```bash
# 0. Stack up (host port 5434 avoids a local PG on 5432)
POSTGRES_PORT=5434 docker compose up -d --build

# 1. Functional checks
docker compose run --rm client                     # expect: 57/57 checks passed
npm test                                           # expect: 18 files, 194/194

# 2. Rate-limit characterization (default budget)
npx autocannon -c 50 -d 5 -p 1 -m POST \
  -H "Authorization=Bearer $KEY" -H "Content-Type=application/json" \
  -b '{"units":"1","idempotencyKey":"rl-probe-1"}' http://localhost:3000/usage

# 3. Raise limits for load stages (test setup)
POSTGRES_PORT=5434 RATE_LIMIT_MAX=10000000 docker compose up -d app
docker compose run --rm -e BOOTSTRAP_ACCOUNT_NAME=loadtest-account \
  -e BOOTSTRAP_API_KEY_NAME=loadtest-key app node dist/scripts/bootstrap-loadtest.js
# raise plan allowances + create users via authenticated API (see §1), then:
export LOADTEST_API_KEY=<key from bootstrap>
npm run loadtest -- --duration 10 --connections 50    # repeat per stage
npm run loadtest -- --duration 60 --connections 500   # sustained

# 4. Correctness probes (scripts archived in 2026-10-18-stress-raw/)
RAW=docs/performance/2026-10-18-stress-raw
node $RAW/idempotency-storm.mjs http://localhost:3000 "$KEY" 200 1
node $RAW/multi-user-load.mjs http://localhost:3000 "$KEY" 10 1 \
  stress-u1,stress-u2,stress-u3,stress-u4,stress-u5,stress-u6,stress-u7,stress-u8,stress-u9,stress-u10

# 5. Invariants (before/after; also after every stage)
POSTGRES_PORT=5434 docker compose run --rm app node dist/scripts/verify-invariants.js

# 6. Restore default rate limit
POSTGRES_PORT=5434 docker compose up -d app
```
