# Load-Test Results — 2026-10-18

Reproducible measurement of the Docker Compose stack on a single development
machine. Numbers describe that environment only; they are not a production
capacity claim.

## Environment

| Item | Value |
|------|-------|
| Date | 2026-10-18 (UTC) |
| Host | Linux x86_64, 12 CPU cores, 7.9 GB RAM |
| App runtime | `node:22-alpine` (Node.js 22.15.0) in Docker Compose |
| Database | PostgreSQL 16.15 (`postgres:16-alpine`) in Docker Compose |
| Cache | Redis 7 (`redis:7-alpine`) — rate-limiter store |
| Rate limiter | Raised to `RATE_LIMIT_MAX=10000000` for the measurement window only; production default is 100 req/60s per layer |
| Load generator | Autocannon via `npm run loadtest` on the host (target `http://localhost:3000`) |

## Method

- Account-scoped `POST /usage` requests, `units=1`, unique idempotency key per
  request, pipelining 1 (no request pipelining; each response awaited).
- Load-test account bootstrapped with `bootstrap-loadtest.ts`
  (account plan: 1,000,000 units/month, 10,000 max/request).
- Every sent request is an authenticated write: counter row lock +
  `usage_requests` insert in one transaction.

Throughput is connection-latency-bound: 10 connections at ~82 ms mean
latency implies ≈122 req/s, which matches the measured 120.40 req/s. The
dominant cost is the per-request database transaction (counter upsert +
`FOR UPDATE` lock + decision-log insert + commit).

## Database Evidence

Queried directly after the run:

```sql
-- Decision log for the load-test account
SELECT ur.decision, COUNT(*), SUM(ur.units)
FROM usage_requests ur
JOIN accounts a ON a.id = ur.account_id
WHERE a.name = 'loadtest-account'
GROUP BY ur.decision;
-- -> accepted: 3622 requests, 3622 units, 0 rejected

-- Account counter for the current period
SELECT uc.counter
FROM usage_counters uc
JOIN accounts a ON a.id = uc.account_id
WHERE a.name = 'loadtest-account' AND uc.user_id IS NULL;
-- -> 3622  (counter == sum of accepted units)
```

Accounting invariants verified for the whole database and for the load-test
account after the run (`docker compose run --rm app node
dist/scripts/verify-invariants.js`): **all invariants hold** — counters equal
accepted totals, stored remainings non-negative, tenant pairing intact.

## Reproduction

```bash
# 1. Start the stack with the rate limiter raised (measurement only)
RATE_LIMIT_MAX=10000000 docker compose up -d --build

# 2. Bootstrap the load-test account and capture the printed key
docker compose run --rm \
  -e BOOTSTRAP_ACCOUNT_NAME=loadtest-account \
  -e BOOTSTRAP_API_KEY_NAME=loadtest-key \
  app node dist/scripts/bootstrap-loadtest.js

# 3. Run the load test (key from the previous step)
export LOADTEST_API_KEY=<key-from-step-2>
npm run loadtest -- --duration 30 --connections 10

# 4. Verify accounting invariants
docker compose run --rm app node dist/scripts/verify-invariants.js

# 5. Restore the production-representative rate limit
docker compose up -d app
```

The load test refuses non-localhost targets (`validateLocalUrl`).
